## Что передаётся

- Код и история проекта в GitHub.
- `mymuse-development.dump`, отдельный снимок текущей PostgreSQL для локальной работы. Он передаётся архивом, не хранится в Git.
- `DEV-ACCESS.txt`, пароль только от локального администратора этого снимка.
- Эта инструкция, локальный Docker Compose и скрипты подготовки.
- `production-security-overlay.patch`, исходники исправлений безопасности, которые уже применены на сервере отдельно от Git.

В копии базы сохранены схема, связи, роли, статусы, цены, бронирования и опубликованный каталог.
Действующие пароли, сессии, коды восстановления, Telegram-привязки, контакты,
приватная переписка и реквизиты платёжных операций удалены или заменены.
Публичные фото могут оставаться доступными по прежним CDN-ссылкам.
Это подготовленная копия для разработки, а не необратимо анонимные данные.

Полная исходная production-копия сохранена отдельно у владельца и не входит в архив разработчика.
Рабочая база при подготовке не менялась. Прямой доступ к ней для локального запуска не требуется.

## Локальная подготовка

Нужны Node.js 22, npm и Docker с Compose. На сервере проверены Node22.23.2,
Next15.5.14, React19.2.4, Nest10.4.22, TypeScript5.9.3, Drizzle0.36.4 и PostgreSQL16.
Старый корневой README содержит устаревшие пути и сведения о таблицах.

Клонировать проект и создать свою ветку:

```sh
git clone https://github.com/kabuto-lab/e1.git MyMuse
cd MyMuse
git switch -c dev/onboarding
git apply --check docs/handover/production-security-overlay.patch
git apply docs/handover/production-security-overlay.patch
node docs/handover/generate-env.mjs .
docker compose --env-file .env -f docs/handover/compose.dev.yml up -d
```

Скрипт создаёт новые локальные JWT, ключ шифрования, пароли PostgreSQL и MinIO.
Существующий `.env` он не перезаписывает. Боевые Т-Банк, Telegram и TON отключены.
SMTP направлен в локальный Mailhog. Все порты Docker привязаны к `127.0.0.1`.

Дождаться готовности PostgreSQL и восстановить предоставленный снимок:

```sh
docker compose --env-file .env -f docs/handover/compose.dev.yml ps
node docs/handover/restore-db.mjs . /path/to/mymuse-development.dump
npm ci
npm run build --workspace=@escort/db
node docs/handover/init-storage.mjs .
```

В Windows вторым аргументом передаётся обычный путь, например
`C:/work/handoff/mymuse-development.dump`.
Восстановление допускается только в пустую локальную БД контейнера
`mymuse-handoff-local`. Существующие таблицы скрипт не удаляет.
Не выполнять bootstrap, seeds или `db:push` поверх восстановленного снимка.

После исправления указанного build-блокера:

```sh
npm run build --workspace=@escort/api
npm run build --workspace=@escort/web
npm run dev:apps
```

Web: http://localhost:3001. Вход администратора: http://localhost:3001/admin-login.
Локальные логин и пароль находятся в `DEV-ACCESS.txt`, не в этой инструкции.
Проверка API: http://127.0.0.1:3000/health. Документация: `/api/docs` на API.
PostgreSQL: `127.0.0.1:15434`, БД и пользователь `mymuse_dev`.
MinIO: `127.0.0.1:19004`, консоль `19005`. Mailhog: http://127.0.0.1:18026.

Dump содержит записи о медиа, но не сами MinIO-объекты. Полный медиабэкап не входит
в передачу. Публичные сохранённые ссылки можно использовать для чтения; новые
загрузки должны идти в локальный MinIO. Production S3-ключи для этого не нужны.

## Проверки и текущие функции

Навигация по проекту: `docs/CODEBASE_GUIDE.md`, `apps/api/src`, `apps/web/app`,
`packages/db/src/schema`, миграции `packages/db/drizzle`.
Старый гид полезен для карты модулей, но не заменяет текущие исходники.

Перед изменениями оплаты прогнать профильные unit-тесты:

```sh
npm test --workspace=@escort/api -- --runInBand --runTestsByPath src/escrow/escrow.controller.spec.ts src/escrow/tbank/tbank-client.service.spec.ts src/escrow/tbank-escrow.service.spec.ts src/bookings/bookings.service.spec.ts src/escrow/ton-escrow.service.spec.ts
```

Дополнительные session-security тесты из серверной накладки требуют отдельную
пустую тестовую БД `security_auth_test` на loopback. Она отличается от снимка для
разработки. Никогда не подставлять production URL в `SECURITY_TEST_DATABASE_URL`.
На сервере прошла 171 профильная проверка, отдельная SQL-репетиция и запуск
собранного API. Старые тесты `auth.service.spec.ts` раньше имели несогласованные
моки зависимостей; полный набор тестов не объявляется зелёным.

Каталог загружается сразу, без выбора фильтра. Загрузка фотографий проверена.
Telegram-бот `@my_muze_bot` подключён на production. Для разработки нужен другой бот.
Метрика использует счётчик111497387 и события `client_register_success`,
`model_register_success`, `client_booking_created`, `client_payment_reserved`.
Локальный трафик не следует отправлять в боевую аналитику.

Т-Банк подключён к боевому терминалу. Проверены подписанный read-only запрос и
webhook200/plainOK с отклонением неверной подписи. Реальная оплата картой при этой
проверке не выполнялась. В локальный `.env` боевые ключи не копировать; для платёжной
разработки нужен отдельный тестовый терминал. Перепроверить полный цикл платежа до
дальнейших изменений бизнес-логики. Бронирование и его финансовое состояние
согласуются с повторными уведомлениями; Telegram-уведомления остаются best effort.

## Production и порядок работы

Сайт работает на Zomro через systemd `mymuse-api` и `mymuse-web`.
Действующий путь: `/opt/mymuse-deploy/current`; публичные запросы проходят через nginx.
API3100 и Web3101 доступны внутри сервера. PostgreSQL15432 и MinIO19000/19001
также слушают loopback. Это не реквизиты для внешнего подключения.
Рабочие секреты находятся в root600 файлах под `/etc/mymuse-deploy` и
`/etc/zomro-security-env`. В архив и репозиторий они не входят.

Панель публикации: https://debutmodels.com/release-desk/?project=mymuse.
Сейчас она использует доступ владельца. Учётная запись предыдущего разработчика
отозвана. Пароль владельца, root SSH и общий доступ ко всему серверу новому
разработчику автоматически не передаются.

Рабочий порядок: отдельная ветка, изменение, тесты, pull request, затем согласованная
публикация. Не использовать старые `vps:after-pull`, PM2-команды,
`ensure:database` или `db:push` на production. Миграции и боевые платёжные действия
разбирать отдельно. Для первого этапа достаточно GitHub, локальной копии БД и
изолированного стенда.
