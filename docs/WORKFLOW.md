# Работа с MyMuse через GitHub

Репозиторий: https://github.com/kabuto-lab/e1. Основная ветка: `main`.

## Обычное изменение

1. Получить актуальный `main` и создать отдельную ветку, например `fix/profile-upload`.
2. Изменить код и добавить проверку поведения, если изменение затрагивает логику.
3. Запушить ветку и открыть Pull Request в `main`. Описать проблему, изменение и проверку.
4. Дождаться зелёного `Project checks`. При ошибке открыть упавший шаг, исправить причину в этой же ветке и повторно запушить.
5. Разработчик с правом записи может сам слить PR после успешных проверок. Отдельное подтверждение владельца на каждый PR не требуется.

Напрямую в `main` не работаем. Старые шесть веток не удаляем: сначала нужно отдельно разобрать их изменения. Правило веток и наличие CI сами по себе не включают защиту `main`; обязательность проверки настраивается отдельно в GitHub Rulesets/Branch protection.

## Что проверяет CI

Workflow `.github/workflows/ci.yml` запускается для PR в `main`, push в `main` и вручную через GitHub Actions. Единственный итоговый check называется **Project checks**. Для защиты `main` нужно выбрать именно его.

Среда: Ubuntu 24.04, Node.js 22, npm 10.9.0 из `package.json`, установка через `npm ci --include=dev` и общий сценарий `node scripts/verify-worktree.mjs`.

Сценарий последовательно выполняет:

- сборку `@escort/db`;
- весь Jest-набор API, включая `session-security.spec.ts`, с `--runInBand`;
- весь Jest-набор Telegram-бота с `--runInBand`;
- frontend regression tests из `scripts/*.test.cjs`, включая начальную загрузку каталога и цели Метрики;
- полную сборку API, бота и Next.js web.

Первая ошибка останавливает check. Ни один падающий тест не исключается. API/Bot Jest-наборы сами обнаруживают все соответствующие `*.spec.ts`. Результат сборки не берётся из Turbo cache.

Для проверки сессий GitHub создаёт отдельный PostgreSQL 16 с пустой БД `security_auth_test`. URL передаётся только через `SECURITY_TEST_DATABASE_URL`; допускается исключительно `127.0.0.1` и это имя БД. Сам integration test создаёт нужные ему таблицы. Миграции приложения и seed в эту БД не запускаются. После job сервис уничтожается.

CI не нужны GitHub Environment secrets, production `.env`, дамп клиента, MinIO с настоящими фото, рабочие токены Telegram, терминал банка или SMTP. Сценарий создаёт временный синтетический `.env`, не наследует секреты из терминала и удаляет только свой неизменённый файл. API-адреса для сборки направлены на loopback; приложение и реальный бот не запускаются. Шрифты текущих версий сохранены в проекте вместе с лицензиями, сборка не обращается к Google Fonts. `npm ci` скачивает зафиксированные зависимости.

## Та же проверка локально

Запускать из чистого клона или отдельного worktree с Node.js 22. У этой рабочей копии не должно быть локальных `.env*` в корне или каталогах приложений; `.env.example` допустим. Сценарий откажется перезаписывать существующий конфиг. Для разработки с собственным `.env` используйте другую рабочую копию.

Пример для PowerShell с Docker Desktop:

```powershell
npm install --global npm@10.9.0
npm ci --include=dev
docker run --detach --rm --name mymuse-security-ci --publish 127.0.0.1:54329:5432 --env POSTGRES_DB=security_auth_test --env POSTGRES_USER=ci --env POSTGRES_PASSWORD=ci-only-not-a-secret postgres:16-alpine
docker exec mymuse-security-ci pg_isready -U ci -d security_auth_test
$env:SECURITY_TEST_DATABASE_URL = 'postgresql://ci:ci-only-not-a-secret@127.0.0.1:54329/security_auth_test'
node scripts/verify-worktree.mjs
docker stop mymuse-security-ci
Remove-Item Env:SECURITY_TEST_DATABASE_URL
```

После запуска контейнера дождитесь ответа `accepting connections` от `pg_isready`. Если ещё не готов, повторите только команду готовности. На каждый полный прогон создавайте новый контейнер: integration test оставляет свои синтетические таблицы. Проверка откажется использовать непустую БД и ничего из неё не удаляет. `ci-only-not-a-secret` является открытым паролем одноразовой локальной фикстуры, использовать его для сервера нельзя.

В Bash вместо PowerShell-присваивания используйте `export SECURITY_TEST_DATABASE_URL='postgresql://ci:ci-only-not-a-secret@127.0.0.1:54329/security_auth_test'`, после проверки `unset SECURITY_TEST_DATABASE_URL`.

## Сборка и публикация

Зелёный PR подтверждает сборку и перечисленные тесты. Он не подтверждает миграции на копии клиентской БД, настоящую оплату, Telegram webhook или загрузку фото в production MinIO.

На момент подготовки этой рабочей ветки production MyMuse состоит из web, API-базы и отдельных исправлений разных версий. Новая рабочая ветка собирает исходники и защитные изменения в одну основу; до отдельного релиза она не является точной копией работающего production и не считается опубликованной.

Merge в `main` ничего не выкладывает на сервер. Публикация выполняется отдельно утверждённым механизмом релиза: с проверкой изменений БД, резервной копией, сохранённым откатом и проверкой сайта после переключения. До этого релиза не правим файлы прямо на production и не запускаем старые `vps:after-pull`, `ensure:database`, `db:bootstrap` или PM2-команды как способ публикации.

Секреты и выгрузки production БД не коммитим. Для нового разработчика используем отдельное окружение и подготовленную копию БД; настоящие ключи банка, Telegram и production-доступы в CI не передаём.
